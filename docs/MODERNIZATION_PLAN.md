# dnSpy modernization plan

Branch: `0000_Update`. Started 2026-10-23.

## Ground rules

- **Backward compatibility:** `dnSpy.Contracts.*` is the public extension API. Changes are additive only; nothing is removed or renamed without an `[Obsolete]` period. User settings files (`dnSpy.xml`) must keep loading.
- **Targets:** keep `net48` (the .NET Framework host) and replace `net5.0-windows` with `net10.0-windows` (current LTS). Whether to drop `net48` is decided at the end of Phase 6, not before.
- **One phase per PR-sized chunk.** Each phase ends with a green build of both TFMs and a smoke test: start the app, open an assembly, decompile it, edit a method, and debug a hello-world app (.NET Framework + .NET 10).
- Submodule forks (ILSpy 2.3, NRefactory, Roslyn EE, Mono.Debugger.Soft) are only touched in the phase that owns them.

## Phase 0: Baseline

1. Build the current tree as-is (`build.ps1 netframework`, then `net-x64`) with the SDKs and VS on this machine. Record warnings and errors.
2. Record which smoke-test steps work today, so later regressions are measurable.

## Phase 1: Toolchain and target frameworks

1. Add a `global.json` that pins the .NET 10 SDK (`rollForward: latestFeature`).
2. `DnSpyCommon.props`: change `net5.0-windows` to `net10.0-windows`.
3. Fix the `IsDotNet` bug: line 13 sets `false` where it should set `true`. It has been there since commit 04915a693, which means the .NET build never imported ConvertToNetstandardReferences or set `CopyLocalLockFileAssemblies`/self-contained. Verify what changes when it is fixed.
4. Re-check the COM reference workaround (`HasCOMReference`). Modern `dotnet build` supports `COMReference` for some cases, so it may be possible to drop the msbuild-only path.
5. `build.ps1`: new TFM. Check that AppHostPatcher still works with .NET 10 apphosts. If not, replace it with the SDK's own apphost settings.
6. Fix new compiler and analyzer errors: nullable, obsoletions (`SYSLIB*`), WPF changes.
7. BinaryFormatter throws on .NET 9+. It is used in `dnSpy.Contracts.DnSpy/Documents/TreeView/Resources/`:
   - `Deserializer` (shows serialized Bitmap/Icon/ImageListStreamer resources): rewrite it on `System.Formats.Nrbf`, which reads the format without loading types. Safer, and works on both TFMs (the NuGet package supports net48).
   - `SerializationUtilities.Serialize/Deserialize` (AsmEditor: create/edit user-type resources): on net10, either use the `System.Runtime.Serialization.Formatters` compat package or show "not supported on this runtime". Decide when we get there.
8. CI: `actions/checkout@v4`, `setup-dotnet@v4` reading `global.json`, `upload-artifact@v4`, and paths for the new TFM.
9. Publish size: `build.ps1` passes `SelfContained=True` and the RID globally, so every project copies the whole .NET + WPF runtime into its own `bin` (needs >10 GB of disk). Make only the app projects (`dnSpy`, `dnSpy-x86`, `dnSpy.Console`) self-contained.
10. Clean up the new net10 warnings (nullability annotations in the BCL, SYSLIB0050/0021, CA2022) and the vulnerable packages (Newtonsoft 12.0.3, System.Drawing.Common 4.7.0 in the Build tools).
11. Re-implement "create serialized image resource" on .NET (write NRBF for Bitmap/Icon/ImageListStreamer); until then it reports "not supported on this runtime".
12. Bump the version to 6.2.0-dev and update the copyright year.

## Phase 3: Roslyn 2.10 → 5.9 (+ the System.Collections.Immutable / System.Reflection.Metadata move)

0. ✅ net48 moved to `System.Collections.Immutable` / `System.Reflection.Metadata` / `System.Composition` 8.0 through MS.VS.Composition 17.13.41 (NetFxAttributes dropped, it was discontinued). ✅ ClrMD 3.1.512801. `app.config` redirects were computed from every assembly in the net48 output (scratchpad `find-redirects.ps1`: lists references whose version differs from the file in the dir). Roslyn 2.10 runs fine on the 8.0 libraries. ClrMD 3 no longer exposes the DAC's special thread types (debugger helper, thread pool timer/wait/gate, suspending EE, shutdown helper), so those `ClrDacThreadFlags` are never set.
1. ✅ `RoslynVersion` 2.10.0 → 5.9.0 (C#/VB compiler, Workspaces, Features, scripting). On net48 this brings `System.Collections.Immutable` / `System.Reflection.Metadata` / `System.Composition` / `Microsoft.Bcl.AsyncInterfaces` 10.0, `System.Memory` 4.0.5, `System.Text.Json` and `System.IO.Pipelines`. `app.config` redirects are now set from the versions of the files in the net48 output (scratchpad `update-redirects.ps1`).
2. ✅ `dnSpy/Roslyn` ported. dnSpy kept its own copies of Roslyn 2.10's QuickInfo providers and C#/VB smart indenters (about 1,800 lines). They're replaced by thin adapters over Roslyn 5.9's own services: `dnSpy.Roslyn.Internal.QuickInfo.QuickInfoService` maps Roslyn's quick info sections to the existing UI content, and smart indent calls Roslyn's `IIndentationService`. Signature help and the editor helpers needed only API fixes (`SemanticParameterIndex`/`SyntacticArgumentCount`, trigger character lists, `Contract`, `IProgressTracker`). Roslyn 5.9's Features assemblies contain VS IntelliCode ("Pythia") parts whose imports only VS exports. System.Composition validates every import, so one of them stopped all C# signature help providers from being created. `RoslynMefHostServices` now builds the container itself and leaves out `*.ExternalAccess.Pythia.*`.
3. ✅ `Roslyn.ExpressionCompiler` rebased onto Roslyn 5.9.0 (35d9211b) on fork branch `dnSpy-roslyn-5.9`. `master` = pristine Roslyn source, `roslyn-5.9-source` = the 5.9 source commit, then a merge with the 43 dnSpy patches. Main changes: generated names are parsed per compiler (`CompilerKind` on `MethodDebugInfo`, so Mono/VB-compiled code still works), `ModuleId` instead of the module version `Guid` (dnSpy keeps `Guid` overloads), C# `RenamedParametersMethodSymbol` now derives from `WrappedMethodSymbol`, and VB's version gained the members new in 5.9.
4. ✅ Smoke test (scratchpad `FeatureProbe`, run on dnSpy's net48 and net10 output, net48 with dnSpy's own `dnSpy.exe.config`): compile + emit + run (the Edit Method path), QuickInfo (semantic and `}`), signature help, smart indent, and the C# expression evaluator (compile expression, error reporting, get locals, assignment) all pass on both. UI test on the .NET 10 x64 build:
   - Edit Method (quick info, signature help and smart indent work in the editor; a C# 12 collection expression compiles).
   - Edit Class (a member using list patterns is added).
   - C# Interactive (Roslyn 5.900, list patterns, raw strings).
   - Debugger: Locals; Watch for arithmetic, function evaluation, array creation, and compile errors.
5. ✅ Cleanup: the now-empty `dnSpy.Roslyn.CSharp.Internal` and `dnSpy.Roslyn.VisualBasic.Internal` projects are removed. MessagePack is pinned to 2.5.307: VS-MEF 17.13 pulls in 2.5.192, which has 3 advisories.
6. Found during the UI test:
   - Fixed: a pattern variable in a watch expression (`x is int y`) gave "Internal debugger error". There were two causes:
     - `RenamedParametersMethodSymbol` hid the EE compilation (NRE).
     - Roslyn can't generate code for EE pattern variables ([dotnet/roslyn#25702](https://github.com/dotnet/roslyn/issues/25702); its own test is skipped). These now report CS8185, like other declarations that aren't allowed.
   - **Known issue:** `out var` in a watch expression compiles but fails at run time with "Internal debugger error". The code that dnSpy's interpreter runs for EE variables is unchanged from 6.1.8, so this is probably an old bug; not investigated further.

## Phase 5: Modern ILSpy decompiler (side by side)

1. ✅ **Spike:** decompile from a dnlib `ModuleDef` with ICSharpCode.Decompiler (11.1.0.9782, the latest stable; 9.x was the plan's guess, 11.x is still netstandard2.0 and needs System.Collections.Immutable/Metadata 9.0, which net48 already has as 10.0). The module is written with `MetadataFlags.PreserveAll`, loaded as a `PEFile`, and tokens map back through the dnlib writer's metadata (318/318 methods matched). Local names come from the PDB dnlib already loaded (`IDebugInfoProvider` over `PdbState`). Still to prove: the IL offset ↔ text maps (`MethodDebugInfo`).
2. ✅ (basic) New extension `Extensions/ILSpyModern.Decompiler`: `dnSpy.Decompiler.ILSpyModern.Core` (the `IDecompiler`, also loaded by dnSpy.Console) and `dnSpy.Decompiler.ILSpyModern.x` (MEF export, content type). Language "C# (ILSpy 11)", GUID `8E0CBE51-4A6E-4C8C-9B3E-2D6D6C1F8A11`, ordered right after the old C# language. The old 2.3-based languages stay as they are.
   - Name clash: the package's `ICSharpCode.Decompiler.dll` has the same name and public key as the 2.3 fork (2.3.1.0 vs 11.1.0.9782), so they can't share a bin dir (and .NET has one default load context). `RenamedICSharpCodeDecompiler.targets` rewrites the package assembly at build time with dnlib (inline `RoslynCodeTaskFactory` task using `Build/compiled/dnlib.dll`) as `dnSpy.ICSharpCode.Decompiler`, signed with `dnSpy.snk`. The 2.3 fork keeps its identity, so extensions that use it still load.
   - References: a `TokenWriter` that writes to `IDecompilerOutput` maps ICSharpCode symbols back to dnlib definitions (main module through the writer's token map; other modules by token), plus `ILVariable`/`let` locals. Assembly references go through dnSpy's dnlib resolver; when it finds nothing (dnSpy.Console, .NET Core targets) through ICSharpCode's `UniversalAssemblyResolver`.
   - To do: cache the converted module between decompilations (now it's written to memory every time; needs a "module changed" signal), settings page, XML doc comments, `DecompileNamespace`/partial types/Export to Project, namespace references.
3. ✅ (statements, locals) Debugger statement mapping: `DecompilerOutputTokenWriter` implements `ILocatable` (line starts are recorded, columns come from `IDecompilerOutput.NextPosition`, so indentation is included), the AST is written through `TokenWriter.WrapInWriterThatSetsLocationsInAST`, and `MethodDebugInfoCreator` turns `CSharpDecompiler.CreateSequencePoints` into `MethodDebugInfo` per `ILFunction` (MoveNext + kickoff method for async/iterators, lambdas and local functions; expression trees skipped). Locals map by IL local index or `StateMachineField`; hoisted parameters by field name (ICSharpCode.Decompiler doesn't record their field). Method span = the function's outermost AST node.
   - To do: `AsyncMethodDebugInfo` (await yield/resume offsets, builder field, SetResult offset; from the PDB's async info when there is one, else IL analysis), `CompilerName`, scopes/imports. Then Edit Method's compilable output and the BAML decompiler.
4. ✅ (partly) Beat ILSpy on the benchmark: `ModernCSharpTransforms.cs` adds two AST transforms that run after ILSpy's own (before parentheses are inserted). `StringConcatToInterpolationTransform`: a `+` chain from `string.Concat` (ILSpy only annotates the outermost `+`) whose operands are all strings, with at least one literal and one non-literal, becomes `$"..."` (braces doubled; skipped in expression trees, constant expressions and when `StringInterpolation` is off). `RemoveImplicitDecimalCastsTransform`: an implicit integral → `decimal` cast whose sibling operand of an arithmetic/comparison operator is `decimal` is removed (IL annotations kept for the statement mapping).
   - To do: switch expressions inside lambdas (ILSpy turns them into statement lambdas with temporaries; 1 of 3 kept), a setting to turn the cleanup off, the NRE in `VisitDirectionExpression` (see the README known issue; not caused by the dnlib rewrite, the PDB, `DecompileTypes` or the location decorator, all checked against plain ICSharpCode.Decompiler 11.1; next suspect: `DnlibAssemblyResolver` resolving different reference assemblies), and Export to Project with this language (`dnSpy.Console -o` says it doesn't support projects).
5. When at parity, make it the default. Remove the old one only after a release with both.

## Questions for the owner

- Phase 5 uses ICSharpCode.Decompiler **11.1** (latest stable) rather than 9.x, and the language is called "C# (ILSpy 11)" (the name follows the package's major version). Say if you want 9.x pinned instead.
- The new package is renamed at build time to `dnSpy.ICSharpCode.Decompiler` so the old ILSpy 2.3 fork keeps its `ICSharpCode.Decompiler` identity (third-party extensions may use it). The alternative is renaming the old fork instead. Keep it this way?
