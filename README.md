# dnSpy

dnSpy is a debugger and .NET assembly editor. You can use it to edit and debug assemblies even if you don't have any source code available.

> **This is a fork of [dnSpy](https://github.com/dnSpy/dnSpy)** (original by 0xd4d, archived in December 2020). dnSpy 7.0 updates the last upstream release, 6.1.8, to current .NET and a current decompiler, and stays backward compatible with it.

## Why this fork

dnSpy is still one of the best tools to look inside .NET programs, but the [original repository](https://github.com/dnSpy/dnSpy) was archived in 2020 and its last release, [6.1.8](https://github.com/dnSpy/dnSpy/releases/tag/v6.1.8), has fallen behind:

- **It can't debug current .NET.** 6.1.8 runs on .NET 5 (out of support since 2022), and the debugger needs `dbgshim.dll`, which .NET 7 and later no longer ship, so debugging a .NET 7–10 app fails with "Couldn't find dbgshim.dll".
- **Its decompiler is from 2017.** The C# decompiler is a fork of ILSpy 2.3: no `async`/`await` (you get the state machine), no switch expressions, pattern matching, local functions, records, `out var` and so on. Modern code comes out hard to read, and often doesn't compile.
- **Its compiler is from 2018.** Edit Method, C# Interactive and the debugger's Watch/Locals expressions use Roslyn 2.10, which doesn't understand C# 8 or later.
- **Its dependencies are old**, several with known security advisories.
- **Nobody maintains it**, so bugs and new .NET releases go unanswered.

The goal of this fork is to keep dnSpy useful for current .NET without breaking anything that works today: existing extensions (`dnSpy.Contracts.*`), saved settings and the .NET Framework 4.8 build all keep working, next to the new .NET 10 build. The old decompiler is still there as a language choice.

## What's new in 7.0

**Runs on and debugs current .NET**
- Builds for .NET 10 (self-contained x64 and x86, nothing to install) and .NET Framework 4.8 (was .NET 5 / .NET Framework 4.8)
- Debugs .NET Core 3.1 and .NET 5–10 apps (new `dbgshim` 10.0), as well as .NET Framework and Unity; launch and attach tested from all four builds
- Recognizes self-contained single-file .NET 6+ apps when starting them under the debugger
- *Prevent managed debugger detection* works on .NET 10 again (`Debugger.IsAttached`, `IsLogging`, `Launch`)

**New default decompiler: C# (ILSpy 11)**
- Based on ICSharpCode.Decompiler 11.1, the current ILSpy engine (the old one was ILSpy 2.3 from 2017)
- **Choose the C# version to decompile to**: C# 1 up to C# 14, or "Latest" (the default). The output only uses that version's features, eg. C# 7.3 gives switch statements and block namespaces, so the code compiles with an older compiler. Set it on the settings page or with `dnSpy.Console --csharp-version 7.3`
- C# features it gives back instead of the compiler's lowered code, among others:
  - `async`/`await`, `await foreach`/`await using`, async streams (`IAsyncEnumerable<T>`), iterators (`yield return`)
  - LINQ query syntax (`from … let … join … group … into`), lambdas, local functions (also `static`), expression trees
  - switch expressions and patterns: type, property, relational (`< 4`), `and`/`or`/`not`, `is` with declarations
  - records and record structs, `init` accessors, `required` members, primary constructors, `with` expressions
  - nullable reference types (`string?`), `default` interface methods, static abstract interface members
  - tuples and deconstruction, `out var`, discards, target-typed `new()`, `??=`, ranges and indices (`a[1..^1]`)
  - `ref` locals and returns, `in`/`ref readonly` parameters, `readonly`/`ref` structs, `Span<T>`/`stackalloc`, `nint`/`nuint`, function pointers
  - string interpolation, `using` declarations, file-scoped namespaces, collection expressions
- Every feature can be turned off on its settings page (anonymous methods, query expressions, async, switch expressions, string interpolation, `using` declarations, …), as well as the old language's options (auto properties/events, `foreach`/`using`/`lock`, object initializers, member order, sorting)
- dnSpy's own clean-up on top of ILSpy's output: `let` clauses instead of `<>h__TransparentIdentifier` chains, switch expressions instead of `?:` chains, string interpolation, no needless casts or `? true : false`, and fixes for code ILSpy writes that doesn't compile
- Full debugger support: stepping (including over `await`), breakpoints, Locals with the decompiled names and correct scopes
- Works with Edit Method, Edit Class, Edit Assembly and Export to Project, with clickable references, XML doc comments and the token/RVA comments of the old language
- Its own settings page (C# language version, member order, every transform can be turned off) and `dnSpy.Console` options
- The old C# (ILSpy 2.3) decompiler is still in the language list; settings saved with it switch to C# (ILSpy 11) once

**Current C# for editing and expressions**
- Roslyn 5.9 (was 2.10): Edit Method, C# Interactive and the debugger's expression evaluator understand C# 14 and current VB

**Export to Project**
- Visual Studio 2022/2026 project options; .NET Core / .NET 5+ / .NET Standard assemblies become SDK-style projects that build
- References to NuGet `System.*` assemblies, WinForms/WPF code-behind split, no compiler-generated types or attributes that break the build

**Fixes**
- Stepping over `await` with the new decompiler ran to the end of the program (fixed in 7.0.0)
- Watch expressions that pass a local or parameter of the current method as `out`/`ref` (`int.TryParse(s, out existingLocal)`) showed "Internal debugger error" (fixed in 7.0.5.0)
- Watch expressions that declare a variable (`int.TryParse(s, out var n) ? n : -1`, `dict.TryGetValue(k, out var v)`) showed "Internal debugger error" (fixed in 7.0.4.0)
- Span collection expressions with `?:`/`??` elements inside `fixed` statements exported as code that doesn't compile (fixed in 7.0.3.0)
- Export to Project of Roslyn (Microsoft.CodeAnalysis.dll) built with 4 errors; a `file` class in a file named PrivateImplementationDetails.cs decompiled to nothing (fixed in 7.0.2.0)
- XAML (BAML) of .NET 5+ WPF apps lost every event handler, and events in templates and style `EventSetter`s were lost on all frameworks; exported WPF projects then built but did nothing (fixed in 7.0.1.0)
- Edit Method could save .NET Framework assemblies that referenced `System.Private.CoreLib` (and crashed)
- Watch expressions with pattern variables (`x is int y`) showed "Internal debugger error"
- Mono debugger: `CustomAttributeNamedArgumentMirror.Field` always returned `null`
- The .NET build never applied its own build settings (`IsDotNet` typo)
- Plus the fixes that come with dnlib 4.5 (generic names in decompiled code, edited resources)

**Updated libraries**
- dnlib 4.5, Iced 1.21, VS-MEF 17.13, ClrMD 3.1, Roslyn 5.9, ICSharpCode.Decompiler 11.1, and updated packages that fix known security advisories (Newtonsoft.Json, MessagePack, MSBuild)

**Build and release**
- Release zips (`dnSpy-netframework.zip`, `dnSpy-net-win32.zip`, `dnSpy-net-win64.zip`) are built by GitHub Actions for every `v*` tag
- CI runs a decompiler regression test and a debugger-info test on every release build, and smoke-tests the zips
- Submodules point to maintained forks, so a recursive clone builds first time

The full list, with details, is in [All changes in detail](#all-changes-in-detail) below; the work log and test results are in [docs/MODERNIZATION_PLAN.md](docs/MODERNIZATION_PLAN.md), and what's planned next is in [docs/TODO.md](docs/TODO.md).

## Binaries

Download the latest release from https://github.com/marinusmaurice/dnSpy/releases. Releases are built by the GitHub Actions workflow (`.github/workflows/build.yml`) when a `v*` tag is pushed; tags with a `-` (eg. `v7.0.0-beta.1`) are published as pre-releases. The last upstream release (6.1.8, .NET Framework 4.8 / .NET 5) is at https://github.com/dnSpy/dnSpy/releases

There are three builds:

| Build | Runs on | Output |
|---|---|---|
| .NET Framework | .NET Framework 4.8 (`dnSpy.exe` 64-bit, `dnSpy-x86.exe` 32-bit) | `dnSpy\dnSpy\bin\Release\net48` |
| .NET x64 | self-contained .NET 10, nothing to install | `dnSpy\dnSpy\bin\Release\net10.0-windows\win-x64\publish` |
| .NET x86 | self-contained .NET 10 (32-bit), nothing to install | `dnSpy\dnSpy\bin\Release\net10.0-windows\win-x86\publish` |

Use a 32-bit dnSpy (`dnSpy-x86.exe` or the .NET x86 build) to debug 32-bit processes.

## Building

Requirements:

- Windows
- .NET 10 SDK (pinned in `global.json`)
- Visual Studio 2026 (or its Build Tools) for `msbuild`, which is needed for the COM reference in `dnSpy.csproj`. Builds have been verified with VS 18 MSBuild.
- About 10 GB of free disk space to build everything

```PS
git clone --recursive https://github.com/marinusmaurice/dnSpy.git
cd dnSpy
./build.ps1                 # everything: net48, .NET x86, .NET x64
./build.ps1 netframework    # or just one of: netframework, net-x86, net-x64
```

Use `--recursive` (or run `git submodule update --init --recursive` after cloning): the ILSpy, Roslyn expression compiler, Mono debugger, TreeView and images code are submodules. After pulling, run `git submodule update --init --recursive` again (or once: `git config submodule.recurse true`).

If the clone or checkout fails with "Filename too long", clone into a shorter folder (eg. `C:\src\dnSpy`) or run `git config --global core.longpaths true` first. Some files are deep in the tree and Windows limits paths to 260 characters by default.

Run it from a *Developer PowerShell for VS* (or put VS's `MSBuild\Current\Bin\amd64` on `PATH`). `./build.ps1 -NoMsbuild` builds with `dotnet` only, which drops the COM reference; it hasn't been re-verified since the .NET 10 update.

`build.ps1` builds one target framework at a time, which leaves each project's `obj\project.assets.json` with only that target. If you have the solution open in Visual Studio afterwards (NETSDK1005 errors), run `msbuild -t:Restore dnSpy.sln`.

Don't use `clean-all.cmd` with uncommitted work: it runs `git clean -xdf`, which also deletes new untracked files.

To debug Unity games, you need this repo too: https://github.com/dnSpy/dnSpy-Unity-mono (or get the binaries from https://github.com/dnSpy/dnSpy/releases/unity)

## All changes in detail

- Targets `net48` and `net10.0-windows` (was `net5.0-windows`), C# language version pinned to 13
- Debugger uses `dbgshim.dll` 10.0 from Microsoft's `Microsoft.Diagnostics.DbgShim` NuGet package (.NET 7+ runtimes don't include it). This replaces the 2017 copy and the `netcorefiles` submodule.
- Fixed: debugging .NET apps from the .NET build failed with "Couldn't find dbgshim.dll"
- Fixed: Edit Method could save .NET Framework assemblies that referenced `System.Private.CoreLib` (and crashed) when a .NET runtime `mscorlib.dll` was loaded in the assembly explorer
- Fixed: with C# 14, `CustomAttributeNamedArgumentMirror.Field` (Mono debugger) always returned `null`
- Fixed: the .NET build never applied the `IsDotNet` build settings (typo since the .NET 5 update)
- Fixed: *Prevent managed debugger detection* didn't hide the debugger from .NET 10 processes (`Debugger.IsAttached`/`IsLogging` became QCalls) and never patched `Debugger.Launch` on .NET 5+. QCalls are now found and patched too.
- Updated libraries: dnlib 4.5.0 (fixes `IEnumerable<!0>` in decompiled code; resources keep their reader type when edited), Iced 1.21.0, Ookii.Dialogs.Wpf 5.0.1, Newtonsoft.Json 13.0.4 and MSBuild 17.14 packages for the build tools (both fix known-vulnerability warnings). `app.config` redirects old dnlib/Ookii versions so existing extensions keep loading.
- VS-MEF 17.13 and ClrMD 3.1
- Roslyn 2.10 → 5.9: Edit Method, C# Interactive and the debugger's expression evaluator now understand current C# (14) and VB. The expression compiler fork is rebased onto Roslyn 5.9.0 with dnSpy's patches. dnSpy's copies of Roslyn 2.10's quick info providers and smart indenters are replaced with Roslyn 5.9's own services. The .NET Framework build now uses System.Collections.Immutable / System.Reflection.Metadata / System.Composition 10.0; binding redirects are generated from the shipped files.
- Fixed: Roslyn 5.9's Visual Studio IntelliCode MEF parts would stop signature help from loading; they're left out of dnSpy's Roslyn MEF container
- Export to Project: VS 2022 and VS 2026 options (VS 2026 is the new default). .NET Core / .NET 5+ / .NET Standard assemblies are exported as SDK-style projects (`net10.0`, `netstandard2.0`, `net10.0-windows` + `UseWPF`/`UseWindowsForms`); before, they got old-style projects that couldn't build. .NET Framework assemblies still get classic projects. Compiler-reserved attributes (`RefSafetyRules`, `NullablePublicOnly`) and compiler-synthesized types (`[Embedded]`) are no longer exported (they broke the build with CS8335).
- Serialized images in resources are read with `System.Formats.Nrbf` on .NET (no type loading)
- Only the app projects are self-contained when publishing (build output went from >10 GB to about 2 GB)
- `build.ps1` retries file moves that antivirus scanners briefly lock, and no longer nests the previous build in `bin\bin\...` when run again
- MessagePack (used by VS-MEF) pinned to 2.5.307 (fixes 3 security advisories)
- Fixed: *Debug → Start Debugging* didn't recognize self-contained single-file .NET 6+ apps (`PublishSingleFile` + `--self-contained`) as .NET apps, so it picked the wrong engine settings (it ran them through `dotnet.exe`). Their host has the runtime linked in, which moves the apphost signature several MB into the file (.NET 10 x64: ~8 MB), past the 512 KB that was searched. The data sections of the exe are now searched too. (The `AppHostInfoGenerator` table is only for .NET Core 2.x / early 3.0 previews, newer apphosts are found by this signature, so it doesn't need new data.)
- Fixed: the .NET release zips (win64/win32) of 7.0.0-beta.1 and beta.2 didn't contain C# (ILSpy 11): the parallel publish built the extension twice at once and one compile failed (CS0009), which CI didn't notice. CI now fails when `build.ps1` fails and runs a smoke test on every release build (`Test/DecompilerStress/check-publish.ps1`: the new decompiler's files are there and the build's own dnSpy.Console passes the decompiler check)
- C# (ILSpy 11): `let` clauses whose value is a switch expression are restored in Debug builds too (ILSpy leaves `<>h__TransparentIdentifier` names there); a decompiler regression test (`Test/DecompilerStress/check.ps1`) runs in CI
- Fixed: watch expressions with a pattern variable (`x is int y`) showed "Internal debugger error"; they now report CS8185 (Roslyn's expression evaluator can't compile them, dotnet/roslyn#25702)
- New decompiler language **C# (ILSpy 11)**, now the **default** language (the old C# language is still in the language list; settings saved with old C# switch over once, later choices are kept). It uses ICSharpCode.Decompiler 11.1 from NuGet, the current ILSpy engine: async/await, `let` clauses, switch expressions, pattern matching, `out var`, local functions, records and so on. It decompiles the module as dnSpy currently has it in memory (so edits show up) and uses the PDB that dnSpy loaded for local names. Types, members, locals and parameters are clickable, and namespaces (in usings, namespace declarations and qualified type names) are references that highlight each other and show a tooltip, like in the old C# language. The package's `ICSharpCode.Decompiler.dll` has the same name and key as the old ILSpy 2.3 fork, so the build renames it to `dnSpy.ICSharpCode.Decompiler.dll` (signed with `dnSpy.snk`) and both ship side by side. `dnSpy.Console -l 8E0CBE51-4A6E-4C8C-9B3E-2D6D6C1F8A11` uses it.
- C# (ILSpy 11) now gives the debugger its statement mapping (IL offset ↔ decompiled text) and the decompiled names of locals and parameters, including hoisted locals/parameters of async and iterator methods and lambdas. It uses ICSharpCode.Decompiler's own sequence points, the same ones ILSpy writes to the PDBs it generates. The debug info also lists the file's `using` namespaces (the expression evaluator uses them to resolve short type names such as `List<int>` in a Watch expression, like with the old C# language) and, for async/iterator methods, the compiler (C#, VB or Mono, from the state machine's name), which the evaluator uses to find hoisted locals.
- C# (ILSpy 11) also gives the debugger the async step info of `async` methods and lambdas (where each `await` yields and resumes, the builder field, the `SetResult()` offset and, for `async void`, the catch handler), so stepping over an `await` can continue after it like with the old C# language. ICSharpCode.Decompiler doesn't expose this, so dnSpy reads it from the state machine's `MoveNext` IL (C# and VB compiler patterns). The IL of an await that ILSpy leaves unmapped (the `IsCompleted` check, the yield/resume code and `GetResult()`) is mapped to the `await` statement.
- C# (ILSpy 11) cleans up three things ILSpy leaves in: `cond ? true : false`, which ILSpy writes for `or` patterns (`o is B or C` → `(o is B || o is C) ? true : false`), becomes `cond` (and `cond ? false : true` becomes `!cond`), and constant operands such as `a || 1 == 0` become `a` (neither inside expression trees); string concatenations of strings with at least one literal become interpolated strings again (`a + ":" + b` → `$"{a}:{b}"`, which the compiler lowers to the same `string.Concat`; not inside expression trees), and casts from an integer type to `decimal` are dropped when the other operand of the arithmetic or comparison operator is already a `decimal` (`(decimal)qty * price` → `qty * price`).
- C# (ILSpy 11) also removes the `bool` temporaries ILSpy leaves for `&&` / `||` whose right operand needed its own statements (an `or` pattern, an `await`): `bool flag = E1; bool flag2 = flag; if (flag2) { bool flag3 = E2; flag2 = flag3; } return flag2;` becomes `return E1 && E2;` (`if (!flag2)` gives `||`). Only for variables with generated names that are used nowhere else, and not when the right operand declares a pattern or `out` variable.
- C# (ILSpy 11) restores switch expressions that ILSpy turns into nested `?:` chains (relational patterns such as `< 4`, which the compiler emits as branches instead of an IL `switch`), e.g. inside a lambda: `Status = g.Sum() switch { 0 => "Inactive", < 4 => "Small", < 8 => "Medium", _ => "Large" }`. Only integer and `decimal` values are handled, and the arms are checked to select exactly the same values as the original chain. A lambda that only declares compiler temporaries and returns an anonymous object built from them (in the same order) becomes an expression lambda again (`x => new { ... }`). The empty `if (1 == 0) { }` statements that ILSpy leaves in Debug-compiled code are removed, and relational patterns are written as `< 4` instead of ILSpy's `<4`. For expression-bodied lambdas, all of the body's IL is now mapped to the body for the debugger (ICSharpCode.Decompiler keeps only the first contiguous IL range of a statement).
- C# (ILSpy 11) has its own settings page (Options → Decompiler → C# (ILSpy 11)) and `dnSpy.Console` options: anonymous methods/lambdas, enumerators, async methods, query expressions, expression trees, switch expressions, string interpolation, using declarations, local names from debug symbols, and a switch that turns off dnSpy's clean-up of ILSpy's output (`--no-dnspy-cleanup`, which gives ILSpy's own output). It also has these options of the old C# language, with the same `dnSpy.Console` names: automatic properties (`--no-auto-props`), automatic events (`--no-auto-events`), `using`/`foreach`/`lock` statements (`--no-using-stmt`, `--no-foreach-stmt`, `--no-lock-stmt`), object/collection initializers (`--no-obj-inits`), `++`/`--` (`--no-inc-dec`), assignment expressions (`--no-make-assign-expr`) and sorting custom attributes (`--sort-custom-attrs`), plus the old language's member order options: the order of nested types, fields, properties, events and methods (`--member-order`, e.g. `mpeft`; on the settings page as five combo boxes), sorting members by name (`--sort-members`) and source code order (`--src-order`: methods, properties and events together in metadata order). The default member order is ILSpy's (`tfpem`, no sorting, no source code order); COM interfaces, enums and the fields of sequential/explicit-layout types keep their metadata order. All are on by default except sorting custom attributes and the two member order switches; the settings are saved in their own `dnSpy.xml` section.
- C# (ILSpy 11) can be used for Edit Method, Edit Class and Add Class Members: when it's the selected language, the code to edit comes from ICSharpCode.Decompiler 11.1 (before, those commands always used the old C# language). The edited members are shown in the main document; the rest of the type is in the hidden document with empty bodies (`return default(T);`, `out` parameters assigned, base constructor calls with default arguments), and the declaring types become `partial`. Constructors that ILSpy leaves out (empty default constructors, static constructors whose code became field initializers) are added back when they're edited. Field initializers stay on the fields (in the hidden document), so they're still part of the compiled constructor. Also fixed in the normal output: the `new()` constraint was written as `new`; `get`/`set`/`init`/`add`/`remove` and `operator` are now the clickable definitions of accessors and operators.
- C# (ILSpy 11) shows XML doc comments (`/// <summary>...`) from the `.xml` file next to the assembly or from the reference assemblies, found the same way as the old C# language (`XmlDocLoader`), with the same XML colors. It can be turned off on its settings page or with `dnSpy.Console --no-xml-doc`.
- C# (ILSpy 11) writes the old C# language's `// Token: 0x06000001 RID: 1 RVA: 0x00002050 File Offset: 0x00000250` comment before each type and member (plus `(get)`/`(set)`, `(add)`/`(remove)` and a delegate's `(Invoke)` method), after the XML doc comment. The token and the addresses are references, as in the old language. It's on by default (like the old language) and can be turned off on its settings page or with `dnSpy.Console --no-tokens`. Edit Method/Edit Class code doesn't get them.
- Edit Assembly (Edit Assembly Attributes) uses C# (ILSpy 11) when it's the selected language (it already did since Export to Project support, but wasn't tested). Its code now compiles: the attributes reserved for the compiler (`[module: RefSafetyRules]`, `[module: NullablePublicOnly]`, error CS8335) are left out, also when their attribute type is embedded in the assembly. The old C# language still writes them, so its Edit Assembly code doesn't compile for assemblies built with C# 11 or later. When the edited attributes are imported, the attributes that can't be written in C# and that the compiler only adds when the code needs them (`RefSafetyRules`, `NullablePublicOnly`, `[assembly: Extension]`) are now kept from the original module. Before, Edit Assembly removed them from the assembly.
- C# (ILSpy 11) supports Export to Project (`.csproj`): one file per type, `Properties\AssemblyInfo.cs` without the attributes the compiler adds again (ILSpy's own list plus `RefSafetyRules`/`NullablePublicOnly`), and WinForms/WPF/settings types split into the code-behind and designer parts (`partial`, `InitializeComponent`/`Connect` and `IComponentConnector` moved out of the code-behind file), like the old C# language. Export to Project no longer writes compiler-generated `<...>` types such as `<PrivateImplementationDetails>` (they aren't valid C#; the compiler creates them again).
- C# (ILSpy 11) now gives the debugger nested local scopes: each local is in the scope of the innermost block of the decompiled code that contains all its uses (the IL of that block's statements, plus unmapped IL next to it such as the `{`/`}` nops), instead of all locals being visible everywhere in the method. So the Locals window and the expression evaluator only see the locals that are in scope where the program stopped, and two locals with the same name in different blocks no longer clash. Hoisted locals of async/iterator methods get the same scopes (the evaluator uses them to pick the right field). Duplicate entries (several ILSpy variables for the same IL local with the same name) are removed.
- C# (ILSpy 11) turns ILSpy's non-compiling ref-local code for a call on a generic `T` value (`ref T reference = ref output; T val = default; if (val == null) { val = reference; reference = ref val; } ... reference.Write(color, text);`, error CS8374) back into the call it came from (`output.Write(BoxedTextColor.Number, version.Major.ToString());`), with the arguments the compiler had to evaluate first put back in place. Only done when the result is evaluated in the same order (the receiver is a local, parameter or field, nothing with side effects is moved). The debugger maps all the IL of the merged code to that one statement.
- C# (ILSpy 11) has a C# language version setting (settings page combo box, `dnSpy.Console --csharp-version 7.3`): C# 1 to 14.0 or "Latest" (the default). It sets ICSharpCode.Decompiler's language version, so the output only uses features of that version (e.g. 7.3: no switch expressions, no file-scoped namespace), and dnSpy's own clean-up respects it. The other options can only turn off more features. Unknown values are treated as "Latest", so a bad value in `dnSpy.xml` still loads.
- C# (ILSpy 11) no longer writes the whole module to memory for every decompilation. The converted module (the copy ICSharpCode.Decompiler reads) is kept for the last 4 decompiled modules, and the referenced assemblies' files for up to 128 assemblies or 256 MB; a referenced file that changes on disk is read again. When a module is edited (Assembly Editor commands, undo/redo, the debugger's in-memory modules) or closed, its copy is dropped, so edits still show up. Decompiling one method of System.Private.CoreLib went from about 430 ms to about 7 ms after the first one, a method of dnSpy.dll from about 60 ms to about 30 ms. `IDocumentTabService.DocumentModified` is now raised before the tabs are decompiled again, so a decompiler can clear its caches first.
- C# (ILSpy 11) handles `[module: DefaultCharSet(...)]`. ICSharpCode.Decompiler assumes `CharSet.Ansi` is the default, so in such an assembly it put `[StructLayout(..., CharSet = CharSet.Unicode)]` on every type, also on enums, interfaces and delegates (which doesn't compile), and it dropped `CharSet = CharSet.Ansi` from types that really are Ansi (the recompiled type then silently became Unicode). Now the module's char set is left out (with the attribute, when only the default layout is left), enums/interfaces/delegates get no `StructLayout`, and Ansi types keep `CharSet = CharSet.Ansi`.
- Fixed: the Debug configuration (what Visual Studio builds) failed with about 25 errors in the C# and VB expression compilers (`MethodSymbolAdapter`, `WithSynthesizedLocalKindAndSyntax`). The Roslyn 5.9 sources use `#if DEBUG` for code that only compiles against Roslyn's own Debug build, and dnSpy uses the Release NuGet packages, so those two projects no longer define `DEBUG`.
- CI uses current GitHub Actions and reads the SDK version from `global.json`. It also builds the Debug configuration (.NET Framework).
- Submodules point to forks under `marinusmaurice` (all upstream branches kept). The Roslyn expression compiler is on branch `dnSpy-roslyn-5.9`; the others are pinned to the same commits as upstream dnSpy.

- 7.0.1.0: the BAML decompiler reads the code-behind's `IComponentConnector.Connect` and `IStyleConnector.Connect` methods from the IL instead of with the old ILSpy 2.3 engine (which couldn't parse them for .NET 5+ WPF apps, where the interfaces moved to `System.Xaml` and `Connect` dispatches with `switch (connectionId - 1)`). For each connection id in the BAML it evaluates the method's dispatch code and turns the id's field stores (`x:Name`, also VB's `WithEvents` properties), event subscriptions, attached events (`AddHandler`) and style `EventSetter`s (created in code, not in the BAML) into XAML again. Export to Project removes `IStyleConnector.Connect` from the code-behind too (the WPF build generates it again), and .NET Framework (classic) projects get `LangVersion latest` (they defaulted to C# 7.3, and C# (ILSpy 11) writes current C#). The BAML decompiler no longer references the old decompiler.
- 7.0.5.0: a local or parameter of the method that's being debugged can be passed as an `out`/`ref` argument in an expression, and the called method changes it in the paused frame. A value type variable's value read from the frame carries its location, which CorDebug passes. A reference type variable's value is kept in a handle (frame values can't be used after the process has run, eg. after a func-eval), so the interpreter passes a `DbgDotNetFrameVariableReference` (new in `dnSpy.Contracts.Debugger.DotNet`, additive) and the CorDebug engine reads the variable from the frame when it calls the method.
- 7.0.4.0: Watch expressions can declare variables (`out var x`). The expression evaluator stores them with the `CreateVariable`/`GetVariableAddress`/`GetObjectByAlias` intrinsics, which dnSpy's interpreter didn't implement ("Internal debugger error"), and `GetVariableAddress` didn't even resolve since the Roslyn 5.9 update (the intrinsics assembly declared it as returning `T*`, the compiler references `ref T`). Each variable now lives in element 0 of a `T[1]` array created in the debugged process, so a called method can write to it: passed as an `out`/`ref` argument, the element's value is passed and CorDebug passes its location (it's no longer boxed). `typeof(T)` values are remembered so the variable's type is known. Variables last for the evaluation.
- 7.0.3.0: in those duplicated `fixed` blocks, a span collection expression's `?:`/`??` elements are written through `ref` locals to the buffer's elements (`r = ref buffer[2]; n = (r = x ?? -1);`, or `n = x ?? -1; r = n;` in the other copy). These element forms are recognized too, and the `ref` locals and temporaries (declared at the start of the method) are removed with the buffer when they're only used there.
- 7.0.2.0: C# (ILSpy 11) Export to Project of Microsoft.CodeAnalysis.dll (Roslyn 5.9, `net10.0`) builds with 0 errors (was 4). `<>y__InlineArrayN` buffers that ICSharpCode.Decompiler declares at the start of a method (it duplicates the code around `fixed` statements) and fills in each copy (`buffer = default; buffer[0] = a; ...; span = buffer;`) become `span = (Span<T>)new T[] { a, ... }` when every use of the buffer is such a sequence. A constructor whose locals before `base(...)` only copy parameters (eg. for a local function's struct closure) and whose base call doesn't use them gets a `: base(...)` initializer (it was a `base..ctor()` statement). A C# 11 file-local type is named `<FileName>F{SHA-256}__Name`, and ICSharpCode.Decompiler hides every type whose name starts with `<PrivateImplementationDetails>`, so a `file` class in a file named PrivateImplementationDetails.cs decompiled to nothing (also in the normal view); such a type is decompiled without restoring string switches (ICSharpCode.Decompiler only hides it when that is on).

## Known limitations

- .NET build: viewing or creating `BinaryFormatter`-serialized resources (other than images) isn't supported because .NET 9+ removed `BinaryFormatter`. Use the .NET Framework build for that.
- C# (ILSpy 11) Export to Project: names that would be ambiguous with a type of another framework the project uses (eg. ASP.NET Core or Windows Desktop assemblies that the module doesn't reference) aren't detected; only the assemblies next to the module's `System.Runtime`/`netstandard` are checked.
- C# (ILSpy 11): a `ref` local that ICSharpCode.Decompiler declares without an initializer (CS8174) is only fixed when the referenced framework has `System.Runtime.CompilerServices.Unsafe.NullRef<T>()` (.NET Core 3.0+, or the System.Runtime.CompilerServices.Unsafe package); in a .NET Framework assembly without it, the declaration stays as ILSpy writes it. Locals of ref struct or pointer types are also left as they are.
- The default C# decompiler is still the ILSpy 2.x fork. With an old C# language version, code that uses newer features can come out as code that doesn't compile (the benchmark with 7.3: attributes on lambdas, `<>f__AnonymousType` names); plain ICSharpCode.Decompiler 11.1 gives the same output. The old C# language writes `[StructLayout(..., CharSet = ...)]` on enums, interfaces and delegates of an assembly with `[module: DefaultCharSet]`, which doesn't compile (C# (ILSpy 11) is fixed, see above). ILSpy's ref-local code for calls on a generic `T` is only cleaned up in the cases listed above, so other shapes can still give CS8374 errors in exported projects. The first decompilation of a big module is still slow (System.Private.CoreLib: about 3 s), because the whole module is written to memory once. In `dnSpy.Console`, references of .NET (Core) assemblies are found with ICSharpCode.Decompiler's resolver because dnlib's default resolver doesn't search the .NET shared framework.

# Debugger

- Debug .NET Framework, .NET and Unity game assemblies, no source code required
- Set breakpoints and step into any assembly
- Locals, watch, autos windows
- Variables windows support saving variables (eg. decrypted byte arrays) to disk or view them in the hex editor (memory window)
- Object IDs
- Multiple processes can be debugged at the same time
- Break on module load
- Tracepoints and conditional breakpoints
- Export/import breakpoints and tracepoints
- Call stack, threads, modules, processes windows
- Break on thrown exceptions (1st chance)
- Variables windows support evaluating C# / Visual Basic expressions
- Dynamic modules can be debugged (but not dynamic methods due to CLR limitations)
- Output window logs various debugging events, and it shows timestamps by default :)
- Assemblies that decrypt themselves at runtime can be debugged, dnSpy will use the in-memory image. You can also force dnSpy to always use in-memory images instead of disk files.
- Public API, you can write an extension or use the C# Interactive window to control the debugger

# Assembly Editor

- All metadata can be edited
- Edit methods and classes in C# or Visual Basic with IntelliSense, no source code required
- Add new methods, classes or members in C# or Visual Basic
- IL editor for low-level IL method body editing
- Low-level metadata tables can be edited. This uses the hex editor internally.

# Hex Editor

- Click on an address in the decompiled code to go to its IL code in the hex editor
- The reverse of the above, press F12 in an IL body in the hex editor to go to the decompiled code or other high-level representation of the bits. It's great to find out which statement a patch modified.
- Highlights .NET metadata structures and PE structures
- Tooltips show more info about the selected .NET metadata / PE field
- Go to position, file, RVA
- Go to .NET metadata token, method body, #Blob / #Strings / #US heap offset or #GUID heap index
- Follow references (Ctrl+F12)
